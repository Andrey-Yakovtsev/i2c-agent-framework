# Протокол: AC Checklist

Компактный чеклист Acceptance Criteria для защиты от дрейфа реализации при компактизации контекста.

## Когда генерировать

При `code-rfc` (Шаг 1, Architect режим Planning): субагент A генерирует вместе с планом реализации.

## Формат файла

Файл: `.i2c/scratch/rfc-[N]-ac-checklist.md`. Максимум **200 слов** — компактность критична.

```markdown
# AC Checklist: RFC-[N]

## Acceptance Criteria
| AC | Текст | Файл:Функция |
|----|-------|-------------|
| AC1 | [точный текст из RFC] | src/foo.py:create_item |
| AC2 | [точный текст из RFC] | src/bar.py:validate |

## Ключевые интерфейсы (сигнатуры)
- `POST /api/items` → `{id, name, status}` | 201/400/409
- `create_item(name: str, owner_id: int) → Item`

## Error-таблица (компакт)
| Ситуация | Код | Сообщение |
|----------|-----|-----------|
| Дубликат | 409 | item_already_exists |
```

## Правила для Architect

- Копируй AC **дословно** из RFC — не перефразируй
- Интерфейсы — только сигнатуры (1 строка каждая), без описания
- Error-таблица — только из RFC, без дополнений
- Маппинг AC → файл:функция берётся из плана реализации

## Правила для Coder

1. **Перед началом модуля** — перечитай `rfc-[N]-ac-checklist.md` (Read tool)
2. **После реализации модуля** — сверь каждый AC из своей задачи с чеклистом:
   - Интерфейс совпадает с сигнатурой? (имена, параметры, типы)
   - Error-коды совпадают с таблицей?
   - AC покрыт кодом?
3. Расхождение → исправь код. Если невозможно без изменения RFC → пометь `[NEEDS CLARIFICATION]`

## Передача coder-агентам

Оркестратор передаёт путь к чеклисту каждому coding-агенту вместе с RFC и задачей. Агент обязан перечитать файл перед началом работы — это защита от потери контекста при длинных сессиях.
